# Opportunity Radar：产品、工程、证据与商业可行性审查

审查对象：`Opportunity-Radar-main` 项目压缩包中的代码与文档。  
审查日期：2026-10-20。  
审查边界：静态代码审查、离线单元测试与本地示例检查；未连接用户的 FreshRSS、llama-server、SMTP 或 Windows Task Scheduler。本文不是针对具体司法辖区的正式法律意见。

## 一、执行结论

项目适合继续作为个人使用的机会情报 MVP，并逐步发展为公开的工程项目；暂不应宣传为“自动发现可赚钱机会的 AI 产品”。当前价值在于把公开信号变成可复核的调查线索，而不是自动证明市场需求。

本轮优化优先修复了可能让报告产生过度结论的工程问题，并强化了安全默认值：

- 仓库中的来源现在全部默认禁用，不再把候选来源包装成已经完成许可审查的来源，也不再携带特定 FreshRSS 实例的 Feed ID。
- 增加来源登记审计命令，检查启用来源的登记完整性、HTTPS、复核日期和重复 Feed ID；可选检查 URL 可达性。
- 修复“一个引文可定位、另一个引文无法定位，却整体被判为可追溯”的证据等级漏洞。
- 商业评分不再仅因模型填写 `revenue_claim` 或宽泛的 `pricing` 词语就获得高付费分；区分明确预算、明确付费意愿、已有付费行为和间接商业词汇。
- 评分权重现在会归一化，并拒绝负权重或总权重为零的配置。
- 共享输出契约和中文风格规范现在实际进入运行时 Prompt；报告记录 Prompt 内容哈希。
- 文章内容变化时会触发重新分析，保留分析历史，并使旧人工标签失效，避免把旧判断误用于已变化的内容。
- HTML 原文链接仅接受 HTTPS，补充移动端表格处理，并保留无第三方图表依赖的内联 SVG。
- 修正 Windows 脚本路径文档中的拼写错误。

优化后离线测试：122 项全部通过。该结果只代表单元测试通过，不代表真实服务集成或来源许可已经验证。

## 二、产品与用户体验判断

### 产品定位

建议将产品定位为“个人机会情报与验证工作台”，目标用户是需要从分散的公开讨论中寻找真实问题、但时间和资金有限的独立开发者、顾问或技术型创业者。

核心输出应回答：

1. 发生了什么？——来源和原始证据。
2. 能确认什么？——明确区分事实、解释与假设。
3. 还缺什么？——需求频率、影响范围、替代方案、买方、付费证据。
4. 下一步如何验证？——低成本实验、成功标准与停止条件。

### 体验改进原则

- 首屏先给结论与关键未知，不用长篇 AI 摘要占据主要空间。
- 评分只作为排序工具，不能取代证据等级和商业成熟度。
- 过滤条目要展示过滤原因，避免用户误以为它们被系统确认“没有价值”。
- 人工复核应保留原判、修正、时间和理由；来源内容变化后，旧复核不应继续被当作当前结论。
- HTML/TXT/邮件共享同一份结构化分析结果，避免不同输出渠道的数字或结论不一致。

## 三、来源真实性与证据链

### 当前机制

程序使用 FreshRSS Fever API 获取文章，不进行任意站点爬取；Feed ID 通过来源登记表明确映射。模型输出的引文会与输入标题和 RSS 摘要进行规范化匹配。来源身份（例如一手用户表达、项目记录、二手报道）与引文是否可定位是两个独立概念。

### 本轮加固

`python -m opportunity_radar.source_audit` 会检查启用来源的关键元数据；`--check-urls` 仅做显式的 HTTPS 可达性检查。启用来源必须填写实际复核日期、最近核验日期、条款 URL、来源域名、内容来源类型及本机 FreshRSS Feed ID。Feed 域名与内容所有者域名不同的桥接源，还必须登记 Feed 提供方及其条款 URL。

### 仍然存在的边界

- URL 可访问不能证明来源身份、内容真实性、法律许可或允许商业再利用。
- `terms_url` 是待人工审查的条款入口，不是自动得出的许可结论。
- HN RSS 桥接源还涉及 Feed 提供方与原始内容平台两侧的规则；两者需要分别核实。
- 当前数据库保存内容哈希和版本记录，但没有保存完整的历史 RSS 正文快照。分析结果保存了引用、定位字段和输入哈希，可用于基础审计；若要完全复现历史输入，应在确认许可与保存期限后再实现受控快照存储。
- 规范化字符位置对应规范化文本，而不是原始 HTML 的字节偏移。后续如需精确回放，应保存规范化文本版本或定位映射。
- 用户论坛中的一条真实发言只证明该用户表达过该问题，不能证明问题普遍存在或有人愿意付费。

### 每个来源启用前的人工清单

- [ ] 核实网站所有者、规范域名与实际 Feed 提供方。
- [ ] 检查当前使用条款、API/RSS 条款及相关内容许可。
- [ ] 明确内部摘要、内容保存期限、引文展示、归属和公开再发布的限制。
- [ ] 确认请求频率、缓存策略、停止访问条件；不绕过登录、验证码、付费墙或技术限制。
- [ ] 在本机 FreshRSS 核对 Feed ID，并填写实际复核日期。
- [ ] 若条款不清楚，保持禁用。

## 四、模型、Prompt 与评分

### 当前架构建议

保留单次受约束模型调用作为默认路径。对当前本地小模型，盲目把每篇文章拆成五个独立 Agent 会增加延迟、令牌消耗和失败面，但未必改善事实准确率。

Prompt 采用职责分离的写法，但当前运行时将证据规则、问题分析、商业判断和中文编辑约束收敛在单次调用中；确定性程序负责来源映射、引文定位、分类规则、评分、准入和输出校验。未来只有在人工标注集证明额外调用能降低错误时，才增加单独的证据提取或反方审查阶段。

### 评分原则

- 现有权重与阈值继续保留，暂不凭直觉调参。
- 付费证据字段必须来自文章文本规则或人工核验，而不能由模型的商业摘要反推。
- 综合分与商业状态分离：高分不是已验证机会；项目发布也不是客户需求。
- 评分版本、Prompt 版本及 Prompt 哈希应一起保留。
- 需要用人工标注数据检验误报、漏报和类别混淆；少量样本不能支持准确率宣传。

## 五、工程与依赖选型

### 继续使用标准库的部分

- `sqlite3`：当前单机、小批量、单用户运行规模足够。
- `urllib`：当前低频、同步 HTTP 请求足够；若将来需要复杂重试、连接池或大量并发，再评估 `httpx`。
- `html.escape`、`urllib.parse`：简单静态 HTML 报告的基础防护。
- 内联 SVG：每日十余条文章的少量横向条形图足够，不需要立即引入 Plotly、Matplotlib 或前端框架。
- `unittest`：当前测试规模足够；没有必要仅为使用 `pytest` 而迁移。

### 何时引入成熟库

- `pandas`：历史样本明显增加，需要复杂分组、回测或数据清洗时。
- `matplotlib`：需要多系列静态图、分布图、误差分析或面向出版的图表时。
- `jsonschema` 或 Pydantic：结构化输出契约复杂化、跨语言复用或数据迁移需求明确时；优先选一个主要方案，不要重复校验。
- `bleach` 等 HTML 清洗库：确实需要展示受信任白名单以外的来源 HTML 时；当前应优先转义纯文本，不渲染来源原始 HTML。

新增依赖前应记录用途、维护状态、许可证、直接/传递依赖、锁定版本和替代方案。

## 六、经济学与商业可行性

机会雷达本身的成本结构较轻：本地模型推理、RSS 读取、SQLite 与静态报告，主要成本是开发维护时间和人工验证时间。其经济价值取决于它是否减少无效调查、提高找到可付费问题的概率，而不是每天产生多少条分析结果。

建议把商业验证流程设计为：

1. 从信号中挑出一个问题假设。
2. 检查官方文档、现有产品和替代工作流。
3. 找到至少 2–3 个相互独立的潜在用户，验证问题是否重复出现。
4. 询问目前如何解决、耗费多少时间/资金、谁决定采购、什么条件下会付费。
5. 优先尝试人工服务、付费诊断或小型试点，而不是先开发完整 SaaS。
6. 只有在重复需求、可接触买方和可行获客路径都出现证据后，再考虑标准化产品。

这 2–3 人是低成本的初步定性验证门槛，不是统计意义上的市场证明。若要声称市场规模、定价或转化率，必须另行收集数据。

## 七、法律与公开发布风险

- 公开访问不等于授权复制、长期保存、商业分析或再发布。
- 仓库应只包含代码、配置模板、虚构样例和可公开的测试；不得提交 `.env`、数据库、日志、个人邮件或未获许可的完整文章。
- 邮件和报告优先保留原文链接与必要短摘录，避免复刻来源文章。
- 对每个来源保留许可/条款审查记录，并设置复审和停止使用流程。
- 需要公开发布大量内容、提供付费服务或部署面向第三方的服务前，应根据适用司法辖区与具体来源条款进行专业法律审查。
- 项目报告应明确它是辅助研究工具，不构成法律、投资或商业成功保证。
