# R2 第八批：N0 + N1 工程实施规格（冻结）

日期：2026-11-01
状态：本文件是第八批的**实施规格与验收依据**，由项目负责人在实施前确认并写入仓库。
执行结果见 `R2_BATCH8_ACCEPTANCE_2026-11-01.md`；现行契约见 `docs/CLAIM_PIPELINE.md`。

## 一、任务目标与边界

基于当前 R2 工作分支，新增两个独立节点：

- **N0：Document Normalization**——文章标准化与字符定位。
- **N1：Numeric Candidate Extraction**——数字候选发现与表达关系识别。

本次的核心目标是解决当前 Claim 生成流程中的数字召回问题。

此前 BEA 文章已经包含相关数字，但模型没有将部分数字转换成 Claim。这说明数字发现不能继续完全依赖第一轮 LLM 分析结果。

因此，新的 N1 必须直接扫描完整文章正文，独立发现数字表达。现有 facts 可以作为后续关联数据，但不能成为 N1 的唯一输入。

### 本次开发边界

1. N0、N1 必须独立于现有 Claim 生成链路。
2. 不修改现有 Claim 契约、核验器、评分规则和生产分析流程。
3. 不提前开发 N2、N3。
4. N0、N1 不调用本地 LLM。
5. 不把 Prefect、DVC 等工作流框架作为本次必要依赖。
6. 不重构现有文章实体、数据库或文档体系。
7. 不为了引入新工具而替换已经正常工作的现有实现。

本次完成后，应当得到两个可独立调用、可重复执行、具有明确输入输出契约的模块。

## 二、开源工具选型与实施原则

先检查现有项目技术栈，再决定是否引入新依赖。

### 1. 工具评估表

| 节点 | 工具 | 评估结论 | 使用边界 |
|---|---|---|---|
| N0 | 现有正文抽取与文本处理逻辑 | 优先复用 | 不重复建设文章抽取系统 |
| N0 | spaCy | 可选 | 仅在句子切分或定位能力确有不足时考虑 |
| N0 | Unstructured | 暂不引入 | 当前任务不需要重建多格式文档解析体系 |
| N1 | Microsoft Recognizers-Text | 优先实测 | 作为数字、货币、日期和时间表达的候选识别器 |
| N1 | 自定义规则 | 必须保留 | 补充项目所需的特定数字表达和边界处理 |
| N2/N3 | llama.cpp JSON Schema / GBNF | 后续复用 | 本次不开发模型节点 |
| N2/N3 | Outlines / Guidance / Instructor | 暂不引入 | llama.cpp 已提供结构化输出能力，本次不需要增加框架 |
| N4 | Pydantic | 可复用或引入 | 后续用于数据契约与字段校验 |
| N4 | Pint | 暂不引入 | 物理单位换算不是当前核心需求 |
| N4 | Babel | 暂不引入 | 不能替代经济数据的币种、数量级和统计口径规则 |
| N5 | SQLite、JSON、hashlib | 优先复用 | 用于节点结果留存、哈希和版本记录 |
| N5 | Prefect / DVC | 暂不引入 | 当前节点数量和运行规模不足以证明引入必要性 |

### 2. Microsoft Recognizers-Text 实测要求

项目地址：https://github.com/microsoft/Recognizers-Text

需要检查其 Python 实现的实际支持情况，包括：

- 百分比；
- 百分点相关表达；
- 货币；
- 普通数字；
- 数量级；
- 日期；
- 时间范围；
- 不同表达形式的字符位置。

重点验证：

- `$92.8bn`
- `USD 12.8 billion`
- `0.2 percent`
- `2 percentage points`
- `1,234,567`
- `-0.5%`
- `2.1–2.5%`

注意：Recognizers-Text 是候选识别器，不是完整的经济指标理解系统。

不得假设它可以识别所有自然语言数字表达，也不得把其 resolution 结果直接当作最终 Claim 数值。

必须保留：

- 原始表达；
- 原文位置；
- 识别类型；
- 识别工具及版本；
- 解析结果（如果有）；
- 识别状态。

如果识别器无法解析某个表达，但能够发现数字文本，应保留候选或未分类数字片段，而不是静默丢弃。

### 3. 工具引入原则

本次只允许在实测证明有收益时引入新依赖。

优先级：

1. 复用现有代码。
2. 使用成熟、轻量的规则识别库。
3. 使用少量项目自定义规则补充。
4. 不为了统一技术栈而增加大型框架。

Recognizers-Text 应先作为独立适配器进行测试，再决定是否纳入正式 N1 实现。

## 三、N0：Document Normalization

### 1. 节点职责

统一文章表示，建立完整正文、段落、句子及字符位置。

不负责：事实抽取、数字识别、指标主体识别、语义判断、数值标准化、Claim 生成。

### 2. 输入契约

```json
{
  "article_id": "article-001",
  "source_id": "bea",
  "title": "Personal Income and Outlays",
  "content": "原始文章正文",
  "content_format": "html",
  "language": "en",
  "source_url": "https://example.com/article"
}
```

字段说明：

- `article_id`：现有文章唯一标识。
- `source_id`：现有来源标识。
- `title`：文章标题。
- `content`：现有系统保存的文章正文。
- `content_format`：html、text 或项目已有格式。
- `language`：语言标识。
- `source_url`：来源地址。

实际实现必须优先复用现有文章模型及正文抽取逻辑，不得重复创建文章实体。

### 3. 输出契约

```json
{
  "document_id": "doc_hash",
  "article_id": "article-001",
  "normalization_version": "n0-v1",
  "content_hash": "sha256",
  "title": "Personal Income and Outlays",
  "text": "标准化后的完整文章正文",
  "paragraphs": [
    {"paragraph_id": "p0001", "start": 0, "end": 120, "text": "..."}
  ],
  "sentences": [
    {"sentence_id": "s0001", "paragraph_id": "p0001", "start": 0, "end": 85, "text": "..."}
  ],
  "offset_unit": "unicode_codepoint",
  "offset_convention": "half_open"
}
```

### 4. 必须保证的行为

**A. 原文可追溯**：所有段落和句子必须能够通过 `text[start:end]` 精确还原。
统一使用 Unicode code point 作为字符偏移单位，使用半开区间 `[start, end)`。

**B. 标准化不能破坏数字定位**：HTML 转文本、空白处理和换行处理必须有明确规则。
字符位置以 N0 最终规范化正文为基准。如果现有正文处理流程已经提供原始内容映射，可以复用；
如果没有，不要为了追踪 HTML 原始字节位置而引入复杂的 Source Map 系统。
但必须保证 N1 的候选位置能够准确定位到 N0 的规范化正文。

**C. 不做语义改写**：不得改写句子、删除数字、将不同段落合并、将 `0.2 percent` 改写为 `0.2%`、
将 `$92.8bn` 改写成其他表达、对数字进行单位换算。数字规范化留给后续 N4。

**D. 正文完整性**：N0 保存现有系统可用的完整文章正文。
不得继续使用 7000 字符截断作为 N0 输出限制。
这里的完整正文指现有文章正文抽取结果，不要求重新抓取整个网页的导航、页脚、广告和菜单内容。

**E. 稳定性**：相同文章内容、相同 N0 版本及相同参数，应产生一致的规范化结果、段落位置和句子位置。

## 四、N1：Numeric Candidate Extraction

### 1. 节点职责

扫描 N0 输出的完整正文，确定性发现数字表达、日期期间表达及其关联关系。

N1 不负责：判断商业意义、判断指标主体、判断某个数字是否应该成为 Claim、判断数字对应的经济指标、
生成 Claim、修改现有 Claim 数据、调用 LLM。

### 2. 输入契约

```json
{
  "document_id": "doc_hash",
  "normalization_version": "n0-v1",
  "text": "完整标准化正文",
  "paragraphs": [],
  "sentences": [],
  "offset_unit": "unicode_codepoint"
}
```

N1 只读取 N0 输出。不直接访问生产数据库，不依赖现有 facts 是否包含相关数字。

### 3. 候选数据分为两层

必须区分：原子候选 Numeric Atom 与复合表达 Expression Group。
不能将 `3.2% to 3.8%` 整体替代两个数字候选。

#### A. 原子候选

| 类型 | 识别对象 | 示例 |
|---|---|---|
| percentage | 百分比 | 0.2%、0.5 percent |
| percentage_point | 百分点 | 2 percentage points |
| currency | 货币金额 | $92.8bn、USD 12.8 billion |
| quantity | 带单位数量 | 5 million vehicles |
| scalar | 普通数字 | 1.5、500 |
| date | 日期表达 | October 2026 |
| period | 统计期间 | Q3 2026、FY2025 |
| ratio | 比率 | 3:1、15 per 100 |
| unclassified_numeric | 尚未分类的数字表达 | 无法由现有规则可靠分类的数字片段 |

同一原文位置可以存在多个有关联的识别结果，但不得无意义地重复生成多个数字事实。
应保留识别器原始结果，并通过关联关系表示不同识别层次。

#### B. 复合表达关系

| 类型 | 示例 | 应保留的信息 |
|---|---|---|
| range | 2.1–2.5% | 起始数字、结束数字及区间关系 |
| from_to | from 3.2% to 3.8% | 两个数字及方向关系 |
| increase_decrease | increased 0.2% | 数字及变化词线索 |
| comparison | compared with 3.2% | 数字及比较线索 |
| temporal_comparison | year over year | 期间和比较口径表达 |

复合表达必须引用已有原子候选的 ID，不得复制出新的独立数字事实。
如果无法识别复合关系，可以保留原子候选，并记录关系未识别状态。

### 4. 输出契约

```json
{
  "document_id": "doc_hash",
  "extractor_version": "n1-v1",
  "candidates": [
    {
      "candidate_id": "candidate_hash",
      "candidate_type": "percentage",
      "raw_text": "0.2 percent",
      "start": 125,
      "end": 136,
      "sentence_id": "s0003",
      "paragraph_id": "p0002",
      "context": "Prices increased 0.2 percent at a monthly rate.",
      "context_start": 90,
      "context_end": 145,
      "detection_method": "recognizers_text",
      "detection_status": "detected",
      "related_candidates": []
    }
  ],
  "expression_groups": [
    {
      "expression_id": "expression_hash",
      "expression_type": "from_to",
      "raw_text": "from 3.2% to 3.8%",
      "start": 200,
      "end": 217,
      "candidate_ids": ["candidate_001", "candidate_002"],
      "detection_method": "regex",
      "detection_status": "detected"
    }
  ],
  "statistics": {
    "candidate_count": 1,
    "expression_group_count": 0,
    "unclassified_numeric_count": 0
  }
}
```

实际字段可以结合项目已有数据结构调整，但必须保留上述语义。

### 5. 字段要求

- `candidate_id`：由文章内容哈希、N1 版本、候选类型、原文位置和原文内容确定；相同输入、相同版本应产生相同 ID。
- `raw_text`：必须与 N0 正文完全一致。
- `start/end`：对应 N0 正文的 Unicode 字符位置。
- `sentence_id / paragraph_id`：必须能够关联到 N0 的句子和段落。
- `context`：至少保留候选所在句子。允许扩展为相邻句子上下文，但不得改变候选自身的字符位置。
- `detection_method`：记录实际使用的检测方式（`recognizers_text`、`regex`、`custom_rule`、`combined`）。
- `detection_status`：至少支持 `detected`、`unclassified`、`ambiguous`。不支持的表达不得静默消失。

### 6. 数字发现与识别器的边界

N1 可以组合使用：Microsoft Recognizers-Text、项目自定义正则、数字 token 扫描、复合表达关系规则。
不同识别器的结果需要合并，并处理重叠和重复匹配。必须保留原始数字位置和识别来源。
对于没有被现有规则分类、但包含数字字符的相关文本片段，记录为 `unclassified_numeric` 或其他明确状态。

不要求把 URL、电话号码、股票代码、文章编号全部当作经济数字，但也不能简单地因为它们看起来像编号，
就在数字发现阶段直接静默删除。N1 的职责是发现和分类候选，后续节点再决定其语义。

## 五、N1 上下文与关系处理

例如：

> Personal income increased 0.4 percent in September, following a 0.3 percent increase in August.

N1 必须发现：`0.4 percent`、`September`、`0.3 percent`、`August`；同时保留所属句子、所属段落、
原始字符位置、相邻表达关系、变化词线索。

但 N1 不应判断：0.4% 是当前月变化率；0.3% 是上个月变化率；两者属于同一个经济指标；
两者是否构成重要 Claim。这些语义判断留给后续 N2、N3。

## 六、N0/N1 验收测试设计

测试采用独立 fixture，不要求人工逐篇标注全部历史语料。

### A. N0 测试

1. 输入 HTML 和纯文本，能够正确生成规范化正文。
2. 正文不发生静默截断。
3. 段落位置正确。
4. 句子位置正确。
5. `text[start:end]` 能还原每个句子和段落。
6. 数字原始表达没有被改写或删除。
7. Unicode 字符、特殊符号、换行不影响定位。
8. 相同输入和版本重复执行结果一致。
9. 空正文和异常格式有明确处理结果。

### B. N1 基本数字表达

| 输入 | 预期 |
|---|---|
| `0.2%` | percentage |
| `0.2 percent` | percentage |
| `2 percentage points` | percentage_point |
| `$92.8bn` | currency |
| `USD 12.8 billion` | currency |
| `5 million vehicles` | quantity |
| `1.5` | scalar |
| `2.1–2.5%` | 两个原子数字 + range 关系 |

### C. N1 变化表达

| 输入 | 必须发现 |
|---|---|
| increased 0.2% | 0.2% + increase 线索 |
| declined by 0.5 percent | 0.5% + decrease 线索 |
| rose from 3.2% to 3.8% | 两个数字 + from_to |
| fell to $92.8bn from $95bn | 两个金额 + from_to |
| up 2 percentage points | 2 percentage points + increase 线索 |

### D. 日期和期间

| 输入 | 预期 |
|---|---|
| September 2026 | date |
| Q3 2026 | period |
| FY2025 | period |
| year over year | temporal comparison |
| month-on-month | temporal comparison |
| over the past 12 months | 数量表达 + 时间期间线索 |

### E. 边界案例

必须覆盖：Article 5；电话号码；URL 中的数字；股票代码；引用编号；10-K；Form 8-K；版本号；
千位分隔符 `1,234,567`；负数 `-0.5%`；括号负数 `(0.5%)`；小数 `0.002`；科学计数法 `1.2e-5`；
重复数字；同一句多个数字；不同句子出现相同数字。

这些测试主要检查候选分类、原文定位及误识别情况。

### F. 定位与可重复性

1. 相同文章运行两次，候选 ID、顺序、位置、原文一致。
2. 每个候选满足 `raw_text == text[start:end]`。
3. 每个候选都能找到所属句子。
4. 每个候选都能找到所属段落。
5. 相邻数字不会错误合并。
6. 不同句子的相同数字不会被错误去重。
7. Unicode 字符和换行不影响定位。
8. 空文章、无数字文章正常返回。
9. 内容变化后，受影响的候选 ID 能正确变化。
10. 复合表达中的 candidate_ids 均能找到对应原子候选。

## 七、实际文章验证

使用此前 R2 第五批 BEA 样本进行实际验证。重点检查以下遗漏数字：

- 0.2%（monthly rate）
- 0.5%
- $92.8bn
- $12.8bn
- $0.1bn

验收只要求：

1. N0 能保留完整正文。
2. N1 能发现上述表达。
3. 原文字符位置准确。
4. 所属句子和段落准确。
5. 能保留必要的日期、期间和上下文。
6. 相同输入重复执行结果一致。

不要求 N1 判断这些数字是不是重要 Claim。

如果 Recognizers-Text 未能识别其中某个表达，需要明确记录，并通过自定义规则或其他确定性方式补充。

### 工具对比要求

至少对比：Recognizers-Text 单独运行；现有规则单独运行；两者组合运行。

记录：候选发现数量；正确定位数量；未分类数量；重复匹配数量；误识别案例；各类表达的支持情况。
不要仅根据总候选数量判断工具效果。

## 八、节点留存与版本管理

N0、N1 应保留可重复运行和追溯能力。优先复用项目现有数据库和存储方式。

至少记录：article_id；document_id；content_hash；node_name；node_version；input_hash；output_hash；
execution_status；executed_at；运行参数；检测工具及版本。

N0、N1 的中间结果应可独立保存和读取。相同输入、相同节点版本、相同参数允许复用历史结果。
如果正文、规则或节点版本发生变化，应产生新的运行结果，不覆盖历史结果。

不要求本次引入 Prefect、DVC 或新的任务调度系统。

---

## 九、节点验收标准

### N0

- 完整正文保留。
- 句子和段落定位准确。
- 原文位置可还原。
- 重复执行结果一致。
- 不发生静默截断。
- 不发生语义改写。
- 不依赖 LLM。

### N1

- 固定测试样本全部通过。
- 五个 BEA 遗漏案例全部发现并准确定位。
- 原子数字和复合表达分层保存。
- 重复执行结果一致。
- 候选关联关系正确。
- 不支持表达有明确记录。
- 不调用 LLM。
- 不生成 Claim。
- 不修改现有 Claim 数据。
- Recognizers-Text 的引入与否有实际测试依据。

不设置无法验证的"所有自然语言数字识别率 100%"目标。
验收范围以明确支持的表达语法和固定测试样本为准，对不支持的表达明确记录。

## 十、执行指令（实施顺序）

1. **检查现有项目**：Git 分支、工作区状态、main 与工作分支关系；文章实体与正文抽取逻辑；
   文本清洗、句子切分与字符定位；数据库与中间结果存储；测试体系与依赖管理；R2 Claim 生成链路边界。
   以实际 Git 状态为准，不假设历史 PR 已合并。
2. **评估工具**：独立测试 Microsoft Recognizers-Text 的 Python 版本兼容性、实体类型、位置与解析结果；
   用本规格的数字表达和 BEA 案例实测；与现有规则比较后再决定是否引入。

## 十一、重要架构决定

**N1 必须扫描完整文章正文，不能只扫描现有 facts。**

如果第一阶段 facts 已经漏掉某个数字，第二阶段只扫描 facts 仍然无法恢复这个数字。因此：

- 完整文章正文是 N1 的主要输入；
- 现有 facts 只能作为辅助关联数据；
- N1 负责尽可能完整地发现数字候选；
- N2 负责识别指标主体；
- N3 负责识别变化关系和统计口径；
- N4 负责数值、单位及数量级标准化；
- N5 负责一致性检查与 Claim 组装。
