# R1 Batch 4（事件级情报展示）— 实施与验收记录

日期：2026-11-01
状态：已实现并验证（生产库副本）；未改变评分权重与发布门禁
上游：`docs/PRD.md` §3 产品形态、`docs/IMPLEMENTATION_PLAN.md` R1 B4

---

## 1. 范围

把已经建好的 Event / Claim / Evidence 模型接到日报，而不是只停留在数据库与命令行。

交付：事件级卡片、主张与其证据定位、来源画像、候选关联状态。不改评分、不改门禁、
不改 RSS/SEC/EIA 的原有入口与追溯能力。

## 2. 卡片结构

一张卡片代表**一个事件**（跨通道全局去重，得分最高的报道作为代表），卡片下按需给出四段：

| 段落 | 内容 | 出现条件 |
|---|---|---|
| 事件结构 | 同事件报道 N 篇 · 报道来源 N 个 · 来源族 N 个 · 独立佐证：是/否 | 多篇报道、多来源族或存在候选关联时；单篇单族不打印，避免每张卡片重复一句无信息的话 |
| 事实主张 | 条数与核验状态分布；每条标注 `[类型·状态]`、引文、证据 ID、定位（`summary@起-止`）与来源 ID | 事件有主张时；正文最多列 2 条，其余提示见归档 JSON |
| 候选关联 | 条数、状态分布、关系与依据，并写明「未经确认，不作为已发生的事实」 | 事件存在候选关联时 |
| 同事件其他报道 | 其余报道的媒体、标题与链接 | 事件有多篇文章时 |

类型标签：`事实 / 来源解释 / 系统推断 / 假设 / 预测 / 观点`；状态标签：
`未核验 / 已核验 / 已否决 / 无法核验`。R2 之前全部是 `未核验`，报告不会出现「已确认事实」的措辞。

归档 JSON（`*.items.json`）中的 `event` 字段保留完整上下文：成员文章、来源、族、独立性分布、
主张条目（含 `evidence_id`、`locator_json`、来源 ID）与关联条目，供事后追溯。

## 3. 生产数据验证（副本）

| 检查 | 结果 |
|---|---|
| 报告渲染 | 16 张事件卡片，全部带主张段；单篇单族事件不再打印冗余结构行 |
| 主张与证据 | 每条主张带证据 ID、`summary@起-止` 定位与来源 ID |
| 候选关联 | 携带 3 条候选的事件卡片输出「候选关联：3 条（candidate 3）· 未经确认，不作为已发生的事实」 |
| 文章不遗漏 | `event_articles` 108 条；有分析但未归入事件的文章 **0**；一篇文章属于多个事件 **0** |
| 证据不丢失 | `claims` 220；无证据的主张 **0**；指向不存在证据的关联 **0** |
| 通道隔离 | 日报中不含 SEC/EIA 标记（`sec-edgar`、`eia:`、`companyconcept` 等）**0 命中** |

说明：那 3 条候选关联属于 NVIDIA 事件，该事件本期未进入阅读区（被来源配额或分数门槛过滤），
因此不在正文卡片中出现；卡片渲染逻辑用同一函数在真实数据上单独验证过。

## 4. 与 SEC/EIA 的边界

本轮要求"端到端验证覆盖 RSS、SEC、EIA"。**SEC/EIA 数据不能进入日报**：G-D2 与项目硬性约束
仍然有效（不写 RSS 业务表、不进 LLM、不进日报）。因此本轮对两个来源的验证在数据层完成：

| 来源 | 验证内容 |
|---|---|
| RSS | 事件、主张、证据、来源画像、候选关联在真实报告中的输出 |
| SEC | 摄取库 2,719 条结构化主张与证据成对存在，定位含 accession / cik / tag / 期间 |
| EIA | 摄取库 34 条观测对应 34 条主张，定位含 series_id / period |

把 SEC/EIA 放进日报需要单独批准（G-D2 第二阶段的独立决策），本批未做。

## 6. 限制

1. 主张仍是 `skeleton`：v5 提示词只产出散文事实，数值字段为空；R2 之后才有可核验数值主张。
2. 正文每事件最多显示 2 条主张，完整列表在归档 JSON；这是为控制报告长度的取舍。
3. 候选关联不参与排序或配额，只作展示。
4. 事件级归并未接入评分与 `priority` 名额；`multi_source_coverage` 证据状态仍按文章计数。
