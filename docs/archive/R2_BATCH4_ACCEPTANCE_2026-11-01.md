## 1. 本地模型服务：16K → 64K

### 1.1 调整前

| 项 | 值 |
|---|---|
| 实际运行（项目脚本 `start-model.ps1` 启动） | `-c 16384`，KV f16，`--n-cpu-moe 48`，`-ngl 99`，`-b 256 -ub 128` |
| 用户交互启动器 `D:\AI\start_server.bat` | 通用默认 8K；Qwen3-30B-A3B 档位默认 2（8K），64K 是第 5 档（q8_0 KV） |

> 记录一处与先前认知不符的事实：管线实际跑的是 **16K**，不是 32K。

### 1.2 调整后

| 项 | 值 |
|---|---|
| Context | **65536** |
| KV 缓存 | `-ctk q8_0 -ctv q8_0`（f16 在 8 GB 卡上装不下 64K；q8_0 实测约 7.3 GB） |
| GPU / MoE 分配 | **未改**：`-ngl 99`、`--n-cpu-moe 48`、`-dev SYCL0` |
| batch / ubatch | **未改**：256 / 128（显存余量约 0.7 GB，放大 batch 会挤掉 KV） |
| 改动位置 | `deploy/windows/start-model.ps1`（管线与计划任务用）；`D:\AI\start_server.bat` 默认档位改为 5（64K） |

### 1.3 实测

| 检查 | 结果 |
|---|---|
| 进程参数 | `-c 65536 -ctk q8_0 -ctv q8_0` |
| 加载日志 | `n_ctx_slot = 65536`，模型加载耗时约 41 秒 |
| `/props` 读回 | `default_generation_settings.n_ctx = 65536` |
| 生成 | 正常，约 10 tok/s（与 16K 时一致） |
| 健康检查 | `/health` = ok |

## 2. 生成预算

| 变更 | 内容 |
|---|---|
| 自适应预算 | `analyzer.output_budget(summary)`：`min(6000, max(2400, 2000 + 长度/4))` |
| 重排上限 | 恢复路径原来固定 2400，长文永远救不回来；改为 `min(6000, 当前预算+1200)` |
| 单篇主张上限 | 提示词从 0–6 改为 **0–8**，并要求"文中有多个数字时覆盖影响判断的那些" |
| 实测 | 50 篇预算区间 2400–2808；仅 1 篇触发重排恢复，全部成功 |

第三批那篇在 2400 处截断的 BEA 个人收入文章，现在单次调用、6 条主张全部结构化。

## 3. 主张质量改进

| 变更 | 内容 |
|---|---|
| `comparison` 词表 | 增加 `monthly_rate`、`quarterly_rate`、`annual_rate`（统计发布用"月度率"表述，此前被判为偏差） |
| 原始表达 | 继续保留 `comparison_raw` 等原文 |
| 单位表 | 增加 metres/kilometres/centimetres/millimetres/kilograms/cells/fps |
| 数字边界 | 修复 `$500bn`、`$1tn` 这类紧贴后缀的数字此前不被解析的缺陷 |

### 3.1 核验规则 r2-v1 → r2-v2（一处必要修改）

**"引文里没有可比数字"从 rejected 改为 unverifiable**。理由：没有可比数字只能说明无法核对，
不能说明被推翻；rejected 只保留给"引文给出了同类数字但与主张不同"。契约版本同时升到 `r2-v3`
（rate 比较词）。

## 6. 限制

1. v7 未启用，生产仍是 v6。
2. 单位表只覆盖本批出现过的物理单位；`million`（无物量）这类"只有数量级"的单位仍会被记为偏差。
3. 关键数字覆盖 70%，仍有约三成带单位的数字未进入主张（受 8 条上限与文章结构影响）。
4. 单侧不可比一律 unverifiable，会让"引文没写但主张写了"的情况不被判为错误——这是有意的保守取舍。
5. 64K 上下文只验证了加载与短生成；长上下文（>16K 输入）的实际速度与稳定性未压测。
