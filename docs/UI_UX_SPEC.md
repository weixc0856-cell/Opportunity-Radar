# Opportunity Radar UI/UX 交互规范

## 1. 信息层级

首屏优先展示：
1. 系统是否健康
2. 最近一次运行成功/失败
3. 当前有哪些来源已启用
4. 最新报告是否生成
5. 是否有待复核线索

不要把“模型分数”作为首页唯一主指标。优先显示证据完整度、待复核数量和运行健康。

## 2. 通用状态

所有异步操作必须具备：
- Loading：明确正在做什么，避免重复点击。
- Success：描述实际完成的动作。
- Empty：解释为什么没有数据以及下一步。
- Error：给出简短原因、可执行排查步骤和日志位置。
- Partial success：明确成功与失败的对象数量。

## 3. 危险操作

- 启用来源：确认其审核状态、Feed ID、条款核验日期。
- 运行日报：运行中禁用重复启动。
- 发送邮件：显示收件人数量，测试发送需要明确确认。
- 修改定时任务：展示时间、任务名称和当前注册状态。
- 覆盖来源列表：显示将被修改的条目数量；保存前校验全部数据。

## 4. 可访问性

- 每个输入都有显式 label。
- 键盘可以访问所有导航、按钮、下拉框和对话框。
- Modal 打开后焦点进入；关闭后焦点回到触发按钮；Escape 可关闭非破坏性对话框。
- 状态不能只靠颜色表达，应同时有文字。
- 文本对比度足够，焦点轮廓可见。
- 表格在窄屏可横向滚动，并保留清晰列标题。
- 发生验证错误时，将错误关联到字段并聚焦首个错误。

## 5. 机会线索卡片（未来 P1）

每条卡片只展示：
- 标题、来源、发布时间
- 一句话信号摘要
- 证据等级和商业阶段
- 为什么值得看 / 主要未知
- 下一步低成本验证
- 原文入口和人工复核状态

不要只展示一个总分；展示评分解释和证据限制。

## 6. 前端实现策略

短期：原生 JS + 分离 CSS/JS + 统一 API client + DOM 转义 + API 测试。  
中期：如果复杂状态和组件明显增加，采用 TypeScript + React/Vite。  
不要在本地 MVP 阶段引入大型 UI 框架而没有组件复用、复杂状态或团队协作需求。
