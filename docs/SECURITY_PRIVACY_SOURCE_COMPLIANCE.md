# Opportunity Radar 安全、隐私与来源合规清单

> 本文是工程风险清单，不是正式法律意见。

## 1. 本地后台安全边界

当前管理后台绑定 `127.0.0.1`，这是正确默认值。不要把 `8090` 映射到公网或局域网，也不要通过反向代理公开。

建议：
- 所有路由统一校验 Host/Origin，而不仅是写请求。
- 限制请求体大小、字段长度和日志读取长度。
- API 错误给用户可操作信息，详细异常只写入本地日志。
- 日志对邮箱、token、授权码、API Key 做脱敏。
- 在 GitHub Actions 或本地提交前执行秘密扫描。
- `.env`、SQLite 数据库、真实日志、个人邮件地址不进入公开仓库。
- 如未来允许局域网访问，先加入认证、CSRF 防护、权限模型、审计日志和安全测试。

## 2. 邮件与收件人

- 163 SMTP 使用客户端授权码，不在 UI 中回显。
- `.env` 文件应加入 `.gitignore`。
- 测试邮件明确显示收件人数量与 SMTP 提交状态。
- 如果向第三方发送，确保收件人确实希望接收该简报，并提供停止发送的途径。
- 不在公开日志或截图中展示完整邮箱地址。
- SMTP 接受提交不等于最终送达，也不等于收件人阅读。

## 3. RSS 和内容使用

- URL 可访问不代表允许全文复制、长期存储、商业再发布或向第三方分发。
- 对官方、媒体、论坛、聚合器和第三方桥接 Feed 分别审查。
- 第三方桥接源需要核验原始平台规则和 Feed 服务商规则。
- 默认仅保存必要元数据、短引文、原文 URL、哈希和分析结果；完整正文快照需单独确定授权和保留期限。
- 不绕过登录、验证码、付费墙、访问限制或技术保护。
- 提供清晰来源归属与原始链接。
- 来源条款变更或无法核实时，将来源禁用并记录原因。

## 4. AI 与提示注入

- RSS 内容是不可信输入，可能包含诱导模型忽略指令的文本。
- 模型不应拥有 shell、任意网络、文件写入或邮件发送工具权限。
- 模型输出必须经 schema 和确定性规则验证。
- 不将模型自述的“有预算”“已付费”直接作为事实；必须能在原文中定位证据。
- 对低置信、引用无法定位、内容变化的分析明确降级并要求人工复核。

## 5. 公开部署前必须重新审查

如果产品变成面向第三方的在线服务，需要重新评估：
- 账号、认证、权限和租户隔离
- 个人信息处理、隐私声明、删除与保留
- 邮件同意、退订和滥用防护
- 来源条款与再分发许可
- 公开 API 的速率限制与滥用防护
- 数据库备份、恢复、监控与事件响应
- 适用司法辖区的法律和消费者保护要求
